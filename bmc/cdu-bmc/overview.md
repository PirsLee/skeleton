# 物理系统

```
        一次侧（facility water）                     二次侧（coolant → IT 负载）
  ┌──────────────────────────────────┐        ┌──────────────────────────────────┐
  │ T_WI / P_WI  ──▶ [过滤器 P_WIF]  │        │  [过滤器 P_CRF] ◀── T_CR / P_CR  │
  │                   │              │        │         ▲                  │     │
  │                   ▼              │        │         │                  ▼     │
  │            [比例阀 VIN_S %]      │  热交换  │   [泵 P1 / P2]      IT 负载      │
  │                   │              │◀──────▶│      (PWM %)          │         │
  │                   ▼              │        │         │              │         │
  │            T_WO / P_WO           │        │         ▼              │         │
  └──────────────────────────────────┘        │   T_CS / P_CS ────────┘         │
                                              │   LPM_C   P_DIFF                 │
                                              └──────────────────────────────────┘
```
- **一次侧**把热量交换给厂务水；**二次侧**把冷量送给IT负载。

- **执行器**只有两个：泵转速PWM_P1/PWM_P2和一次侧比例阀开度VIN_S。

- 泵决定二次侧的流量与压差；阀决定换热量的多少，从而决定供液温度。

- 环境侧：Ta/RH/DPT是环境有关指标。

# 控制

|模式|泵在调节什么|阀在调节什么|典型用途|
|---|---|---|---|
|DP-Temp|二次侧压差P_DIFF->目标压差|供液温度T_CS->目标温度|保证末端有压力|
|Flow-Temp|二次侧流量LPM_C->目标流量|供液温度T_CS->目标温度|保证末端有流量|

# 业务流程

业务流程一般是某个东西的产物，而这个东西一般就是某种要做的事情的详细或者不详细的idea

这样的idea通常有三类：

1. 明说
2. 隐含
3. 沉默

## 生成业务流程通用原理

> 流程 = 某个变量在某项不变量约束下的变化。

> 要枚举流程，就要枚举各种（变量，不变量）的组合。基础的就是不变量分为哪几类。

> 流程是以不变量为基础的。流程存在的理由是：不是维护不变量，而是应对某一种具体的违反方式。同一组不变量有及条违反路径，就有几组流程。也就是说先试着让破坏不可能，做不到的才变成流程。

> 我以为的一种流程就是：从idea --> 不变量与业务流程 --> OO设计与实现（识别角色和职责）。实际上我以为的这个实现方式就是默认每个不变量都要生成流程，实际上第一反应应该是：能不能让它在结构上就不可能被违反。从结构上消灭这样的问题比从运行时消灭要优：因为0流程、0节拍、0失败模式也就是不用写降级路径，违反的是编译错误而不是现场运行错误，且不需要测试会不会违反，因为根本就不可能违反。

> 事实上，从流程到OO中间还有一些关键的步骤需要注意：

1. 调度模型（在命名类之前决定）

流程的节拍与优先级决定了执行模型，执行模型决定了对象是否共享、是否线程安全、是否跨进程。这一步必须先于OO：

调度模型是关于“对象怎么被持有、被谁调用”的问题，写在类定义之前。先确定调度，类的形态才能有着落。

2. 对象边界由“被保护/被共享的东西”决定，不是由流程决定

以执行器写权为例

```
5条流程都想写同一个PWM值：
启动序列/PID/手动/安全动作/停机归零
```
如果按照流程划分对象，写权这个概念会被复制进5个类，然后靠约定维持一致——必然失败。

正确的做法是，反过来问：**什么东西被多条流程共享？**

```
被共享的：
    写权    -->     必须提升为独立实体
    快照    -->     独立实体
    配置与阈值      -->     独立实体（写一次，多方读）
    锁存状态        -->     独立实体（掉电保持，多方读写）
```

**领域模型是先于流程还是后于流程？这个之间的关系是怎么样的？**

领域模型有三种语境：

|语境|内容|与流程的关系|
|---|---|---|
|物理/领域实在|热交换、泵、阀、冗余对、冷凝边界|先于一切，且由客观决定|
|本体|有哪些概念、身份、边界、生命周期、分类|先于流程|
|协作|谁持有谁、谁在什么时机调用谁|后于流程|

且协作领域模型与本体领域模型是一个环回关系，在协作的同时修正本体模型。

且领域模型正是OO设计中识别出角色和职责的基础，或者说领域模型是面向对象分析与设计的基础。

**9个提问模板**

这些基础和具体领域无关，只和“系统必须维持什么有关”

|#|基础|不变量形态|生成的流程类型|
|---|---|---|---|
|1|时间|顺序、时限、速率|循环、延时、超时、窗|
|2|守恒|收支必须平衡|派生量计算、有效性校验|
|3|容量|不得越界|限幅、预警、淘汰|
|4|因果|A必须在B之前|启动编排、事务边界、初始化序|
|5|唯一所有权|同一时刻只有一个写者|锁、优先级、抢占|
|6|一致性|所有观察者看到同一真相|快照、版本、原子提交|
|7|权限|只有授权者能改变|认证、升级、确认、审计|
|8|累积|总数必须准确|计数、累积、对账|
|9|归属|成员关系是确定的|加入/离开、角色、选举|
|-|熵|不变量必然被破坏|看门狗、重连、载断、降级|
|-|拓扑|可达性|发现、寻址、路由|

这些真正的用法就是九个提问模板，针对流程前的领域模型（多数情况下物理/领域实体模型层，本体层是由物理/领域实体模型层派生出来的）的每个对象，每个基础只问一个问题，也就是一个对象用九个问题扫描一遍。

|不变量|高产出信号|问题|产出|
|---|---|---|---|
|时间|出现任何数字、时间单位|在哪两个时刻之间必须保持关系|时间基清单|
|守恒|任何总计、差分、净值字样的字段|这个量从哪里进来、从哪里出去、差额去哪里了？|派生量清单|
|容量|任何表示容量的字段以及存储相关的|最多装多少？满了会怎么样？|饱和状态必须是显示概念。|
|因果|任何设置后生效、重启后、下次启动时等词条，总之，顺序|谁导致谁？反方向可能吗？|同一拍是非法假设|
|唯一所有权|模式选择、角色、当前生效的等词汇|同一时刻只能有一个主体持有/写吗？|仲裁表|
|一致性|任何字段名在之前领域模型中出现过两次以上|同一件事被记在两个地方吗？|权威表|
|权限|不可修改、需二次确认，可以做什么不可以做什么|谁可以改/做？在什么条件下？|权威的前提状态|
|归属|任何有归属关系的结构|属于谁？能同时属于两个吗？离开会怎么样？|关系的生命周期比成员本身长|
|累积|涉及到数量等词，如时数、次数、寿命、Reset、Delete|只会增加吗？谁能让它归零？|破坏性操作清单|
|熵|什么不可能保持？|什么必然变坏？我为什么无法阻止？|容错不变量|
|拓扑|冗余、双、主备、主从、网段|怎么连的？连接形状变化会怎么样？|拓扑前提|


**时间基清单中的时间类型必须一次性说清楚：谁能够整除谁、谁驱动谁、谁是否可以独立。如果只使用独立的定时器而不分清楚这些时间基的关系，后面必然会出现时间基的耦合。**

**派生量清单可以明确哪些量是派生的、哪些是源头。清单一旦定下，唯一写权就自动确定：派生量不允许被独立写入，只能计算，这是守恒基自动带来的。**

**饱和状态如果不显式指明，会造成一些状态产生的行为的差别。**

**同一拍中的拍指的是控制周期、扫描周期、事件处理周期。同一拍是非法假设指的是一个拍内，采集、决策、输出有严格的因果顺序。不能假设这一拍写出去的命令，能在这一拍内被被控对象执行、被传感器读到、再拿来修正这一拍的决策。输出对系统的影响最早只能在下一拍内被观察到。因此控制循环只能是：采集第k拍的快照->及与第k拍快照决策->输出第k拍命令->等第k+1拍再采集验证。如果再输出后立刻回读并调整，实际上是在假设零延迟、瞬时传播、无限采样、这就是零延迟系统的幻想。**

**仲裁表指的是把优先级/抢占关系提升为一等本体概念，每拍由一个仲裁器按仲裁表产生唯一执行器命令；加上mutex之类的锁只能保证串行，不保证谁该，所以真正的设计产出是仲裁表，不是锁。**

1）五个来源同时写两个执行器，本质是语义并发，这些不是普通线程在抢占共享变量，而是同一控制节拍内多个合法控制意图同时作用用于泵和阀。每拍需要一个仲裁器，且仲裁必须有优先级。

2）为什么安全可抢占和唯一写权会冲突。唯一写权指的是每一个节拍内只有一个写者写执行器，安全可抢占指的是C701-C703这类安全源要能随时覆盖普通源。如果没有显式Priority本体，实现里就ihui编程多个写路径相互打架：安全源可以直接写、普通源也直接写、靠mutex或标志位协调，乱成一团且无法维护。这就是跨基冲突——因果基给了每拍的边界，唯一写权基给了单写者，但是缺少一个概念把谁在什么条件下赢统一表达。最终的形式就是不同的源抢占发生在决策/仲裁阶段（高优先级的在这个阶段胜出），唯一写权发生在输出阶段（执行器驱动层只接收仲裁器的唯一命令）。在有仲裁器的前提下，安全请求可以请求锁存，直到复位/恢复条件满足，且普通源也不能绕过仲裁器直接写。

3）mutex为什么不是解决安全与唯一写权的好的解决办法。因为mutex只解决“不能同时写”的并发互斥，不能解决：

- 谁胜出

- 不同源之间的优先级

4）仲裁表样例

|执行器|请求来源|条件/模式|优先级|是否可抢占|输出动作|锁存/恢复|
|---|---|---|---|---|---|---|
|泵|Control Mode PWM|自动运行|低|可被安全源抢占|PWM/转泵|条件恢复
|泵|Manual|手动|中|可被安全源抢占|直接写|切回自动无忧|
|泵|C101巡检|巡检|中|可被低水位/急停抢占|转泵|巡检结束|
|泵|C702低水位|低水位|高|抢占普通源|停泵|水位恢复+迟滞|
|泵|C703急停|急停|最高|无条件抢占|关阀|锁存/人工复位|

**一致性基先产出权威表，规定每个量谁说了算；当权威不可用时，必须有quality这个L2的概念，否则0和不可用无法区分，派生副本只能不知道。最强的实现不是运行时加锁守卫副本，而是在结构上消灭不一致，即让副本类型不可写——const视图、单一存储、计算属性、唯一写者。**

1）这不是异常处理的实现细节，而是数据本体的一部分。因此这部分的产出是权威表+质量状态+失效传播规则。

2） 副本是相对于权威源的任何冗余表示。可以在任何地方。

**权威的前提状态与案例：二次确认与状态对象**

1） 权威的前提状态：也就是说当一个策略依赖于另一个策略的时候，需要将另一个策略变成参数的计算属性，由策略集中求值。

2） 有很多概念在第二层，且需要在第二层发明中间概念。

**关系有自己的ID、属性、生命周期和历史，成员只是引用它的角色；成员换了，关系还在。**

例子：

```
PumpRelation {
    relation_id : "id1",
    type : sometype,
    members : {pump:p1, valve:v1},
}

ok，现在p1坏了换成p2,只需要memebrs.pump=p2，而relation_id并没有变化，所有的其他的东西全部都保留。
```

**破坏性操作清单指的是：系统里所有一旦执行，信息就不可恢复或状态不可逆的操作显示枚举出来的清单，作为一张一等设计清单；每个操作必须挂同一条不变量：授权+二次确认+留痕+影响范围+恢复策略， 以一个破坏性操作清单实例为例：**
