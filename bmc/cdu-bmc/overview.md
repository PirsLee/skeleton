# 物理系统

```
        一次侧（facility water）                     二次侧（coolant → IT 负载）
  ┌──────────────────────────────────┐        ┌──────────────────────────────────┐
  │ T_WI / P_WI  ──▶ [过滤器 P_WIF]  │        │  [过滤器 P_CRF] ◀── T_CR / P_CR  │
  │                   │              │        │         ▲                  │     │
  │                   ▼              │        │         │                  ▼     │
  │            [比例阀 VIN_S %]      │  热交换  │   [泵 P1 / P2]      IT 负载      │
  │                   │              │◀──────▶│      (PWM %)          │         │
  │                   ▼              │        │         │              │         │
  │            T_WO / P_WO           │        │         ▼              │         │
  └──────────────────────────────────┘        │   T_CS / P_CS ────────┘         │
                                              │   LPM_C   P_DIFF                 │
                                              └──────────────────────────────────┘
```
- **一次侧**把热量交换给厂务水；**二次侧**把冷量送给IT负载。

- **执行器**只有两个：泵转速PWM_P1/PWM_P2和一次侧比例阀开度VIN_S。

- 泵决定二次侧的流量与压差；阀决定换热量的多少，从而决定供液温度。

- 环境侧：Ta/RH/DPT是环境有关指标。

# 控制

三种控制模式实际上也就是两个执行器的不同的分工协作模式。

|模式|泵在调节什么|阀在调节什么|典型用途|
|---|---|---|---|
|DP-Temp|二次侧压差P_DIFF->目标压差|供液温度T_CS->目标温度|保证末端有压力|
|Flow-Temp|二次侧流量LPM_C->目标流量|供液温度T_CS->目标温度|保证末端有流量|
|Manual|不自动调节，操作员指定泵号+转速|不自动调节，操作员指定开度|调试/故障处理|

# 业务流程

业务流程一般是某个东西的产物，而这个东西一般就是某种要做的事情的详细或者不详细的idea

这样的idea通常有三类：

1. 明说
2. 隐含
3. 沉默

## 生成业务流程通用原理

> 流程 = 某个变量在某项不变量约束下的变化。

> 要枚举流程，就要枚举各种（变量，不变量）的组合。基础的就是不变量分为哪几类。

> 流程是以不变量为基础的。流程存在的理由是：不是维护不变量，而是应对某一种具体的违反方式。同一组不变量有及条违反路径，就有几组流程。也就是说先试着让破坏不可能，做不到的才变成流程。

> 我以为的一种流程就是：从idea --> 不变量与业务流程 --> OO设计与实现（识别角色和职责）。实际上我以为的这个实现方式就是默认每个不变量都要生成流程，实际上第一反应应该是：能不能让它在结构上就不可能被违反。从结构上消灭这样的问题比从运行时消灭要优：因为0流程、0节拍、0失败模式也就是不用写降级路径，违反的是编译错误而不是现场运行错误，且不需要测试会不会违反，因为根本就不可能违反。

> 事实上，从流程到OO中间还有一些关键的步骤需要注意：

1. 调度模型（在命名类之前决定）

流程的节拍与优先级决定了执行模型，执行模型决定了对象是否共享、是否线程安全、是否跨进程。这一步必须先于OO：

调度模型是关于“对象怎么被持有、被谁调用”的问题，写在类定义之前。先确定调度，类的形态才能有着落。

2. 对象边界由“被保护/被共享的东西”决定，不是由流程决定

以执行器写权为例

```
5条流程都想写同一个PWM值：
启动序列/PID/手动/安全动作/停机归零
```
如果按照流程划分对象，写权这个概念会被复制进5个类，然后靠约定维持一致——必然失败。

正确的做法是，反过来问：**什么东西被多条流程共享？**

```
被共享的：
    写权    -->     必须提升为独立实体
    快照    -->     独立实体
    配置与阈值      -->     独立实体（写一次，多方读）
    锁存状态        -->     独立实体（掉电保持，多方读写）
```

**领域模型是先于流程还是后于流程？这个之间的关系是怎么样的？**

领域模型有三种语境：

|语境|内容|与流程的关系|
|---|---|---|
|物理/领域实在|热交换、泵、阀】冗余对、冷凝边界|先于一切，且由客观决定|
|本体|有哪些概念、身份、边界、生命周期、分类|先于流程|
|协作|谁持有谁、谁在什么时机调用谁|后于流程|

且协作领域模型与本体领域模型是一个环回关系，在协作的同时修正本体模型。

且领域模型正是OO设计中识别出角色和职责的基础，或者说领域模型是面向对象分析与设计的基础。

**九类抽象基础**

这些基础和具体领域无关，只和“系统必须维持什么有关”

|#|基础|不变量形态|生成的流程类型|
|---|---|---|---|
|1|时间|顺序、时限、速率|循环、延时、超时、窗|
|2|守恒|收支必须平衡|派生量计算、有效性校验|
|3|容量|不得越界|限幅、预警、淘汰|
|4|因果|A必须在B之前|启动编排、事务边界、初始化序|
|5|唯一所有权|同一时刻只有一个写者|锁、优先级、抢占|
|6|一致性|所有观察者看到同一真相|快照、版本、原子提交|
|7|权限|只有授权者能改变|认证、升级、确认、审计|
|8|累积|总数必须准确|计数、累积、对账|
|9|归属|成员关系是确定的|加入/离开、角色、选举|
|-|熵|不变量必然被破坏|看门狗、重连、载断、降级|
|-|拓扑|可达性|发现、寻址、路由|

**将九类抽象基础转成流程**

每类基础问三个问题，各自生成一条流程：

|问题|生成|
|---|---|
|谁在维持它|常驻循环|
|它被破坏时怎么办？|告警+恢复|
|破坏后如何重建？|状态机+事务|

最后生成的基础流程大概就是9X3=27,少于这个数量肯定是有流程没有考虑进去，这就是最基础的可动工的流程。也就是根据识别出的不变量的类型确定的基本的业务流程。
