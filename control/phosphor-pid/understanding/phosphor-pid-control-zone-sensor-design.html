00设计骨架速览

整个 daemon 的数据流可以压成一条七段流水线。作者的取向非常明确：配置模型（conf::*）与运行模型（Sensor/Zone）彻底分离， 中间由一对 builder（buildSensors / buildZones）完成「字符串 → 对象」的翻译。运行期只有一个可变状态中心（Zone），传感器只是被查询的只读资源。

一句话总结：Zone 是「状态 + 策略」，Sensor 是「身份 + I/O 能力」，Controller 是「算法」。 三者的耦合被收紧到 interfaces.hpp 一处；pid/ 永远不 #include dbus/ 或 sysfs/， 这条不变量是整个设计能成立的根基。

为什么 SensorManager 是全局单例，而 Zone 是每区一个？

因为这两类对象的共享维度不同：传感器是物理资源（风扇、温度点），天然被多个 zone 同时观测，重复实例化会带来 D-Bus match 重复与 sysfs fd 重复； 而 zone 是控制单元，每个 zone 的 setpoint、fail-safe 表、日志文件都是私有的，没有共享必要，强行共享反而要加锁。

收益Sensor 的读取路径零同步；Zone 的状态无锁（单线程 asio 回调驱动）。
代价Zone 只能按名字查传感器（_mgr.getSensor(name)，名字错了抛异常），编译期无法校验 zone 引用的传感器是否存在——这个校验被推迟到 buildZones 的运行时（源码里还留着 TODO(venture): Need to check if input is known to the SensorManager）。
02Sensor 的三层抽象：薄基类 + 策略注入 + 双重身份

sensors/ 只有 8 个文件、628 行，但把「读什么」「怎么写」「谁发布的」三件事拆得干干净净。 作者的策略是：基类只放身份与策略，绝不放值；值永远由读取的那一刻产生，由 Zone 缓存。

2.1 第一层：Sensor —— 只存身份与策略sensors/sensor.hpp · 83 行

class Sensor
{
  public:
    // 唯一一处「类型 → 策略」的默认推导：风扇没有超时，其他 2 秒
    static int64_t getDefaultTimeout(const std::string& type)
    {
        if (type == "fan") { return 0; }
        return 2;
    }

    Sensor(const std::string& name, int64_t timeout,
           bool ignoreFailIfHostOff = false);

    // 纯虚：唯一的 I/O 契约
    virtual ReadReturn read() = 0;
    virtual void write(double value) = 0;

    // 带默认实现的扩展点：老适配器不用改
    virtual void write(double value, bool force, int64_t* written)
    { write(value); }
    virtual bool getFailed() { return false; }
    virtual std::string getFailReason() { return "Unimplemented"; }

  private:
    std::string _name;
    int64_t _timeout;
    bool _ignoreFailIfHostOff;   // 主机下电时不判失效
};

为什么基类不保存「当前值」？

因为值的生命周期与传感器对象的生命周期不同。传感器对象常驻，但值每 100ms 刷新一次，且「旧值」本身是有语义的（超时判定要用 ReadReturn::updated 时间戳）。 如果把值放在 Sensor 里，Zone 就得反过去问 Sensor 要时间戳、要两个 zone 各自加锁；作者选择让 read() 返回一个自描述的值对象，Zone 拿到就存进自己的缓存，Sensor 保持无状态。

收益Sensor 可被任意多个 zone 并发调用而不需要锁；类型系统上不可能出现「两个 zone 看到不同的当前值」。
代价每次读取都要走一遍适配器（可能是一次 D-Bus 调用），无法做 Sensor 内部的一次性缓存。

ReadReturn 的设计正是这个决策的物化——它把「值 + 时间 + 原始值」打包：

struct ReadReturn
{
    double value = NaN;                       // 归一化后的值（用于 PID 计算）
    std::chrono::high_resolution_clock::time_point updated;  // 采样时刻（超时判据）
    double unscaled = value;                  // 原始值（RPM / 裸温度）
};

2.2 第二层：PluggableSensor —— 策略模式，I/O 由外部注入sensors/pluggable.hpp · 39 行

class PluggableSensor : public Sensor
{
  public:
    // “A Sensor that can use any reader or writer you provide.”
    PluggableSensor(const std::string& name, int64_t timeout,
                    std::unique_ptr<ReadInterface> reader,
                    std::unique_ptr<WriteInterface> writer,
                    bool ignoreFailIfHostOff = false);

    ReadReturn read() override { return _reader->read(); }
    void write(double value) override { _writer->write(value); }

  private:
    std::unique_ptr<ReadInterface> _reader;
    std::unique_ptr<WriteInterface> _writer;
};

这是整个代码库里最关键的 8 行：它把 Sensor 的继承体系从「N×M 种组合」压成「N + M 个适配器」。 读的维度有 4 种（sysfs / D-Bus passive / D-Bus active / write-only），写的维度有 5 种（sysfs 原始 / sysfs 百分比 / D-Bus 原始 / D-Bus 百分比 / 只读）， 如果按多重继承做就是 20 个类；用注入只需要 9 个适配器类 + 1 个组合壳。

2.3 第三层：HostSensor —— 既是传感器，又是 D-Bus 服务sensors/host.hpp · 61 行

class HostSensor : public Sensor,
                  public ValueObject   // = ServerObject<Sensor::server::Value>
{
  public:
    static std::unique_ptr<Sensor> createTemp(
        const std::string& name, int64_t timeout, sdbusplus::bus_t& bus,
        const char* objPath, bool defer,
        bool ignoreFailIfHostOff = false);

    void value(double v) override;   // 外部写进来（属性 setter）
    ReadReturn read() override;          // 读自己缓存的 _value
    void write(double value) override;
    bool getFailed() override;

  private:
    std::mutex _lock;                // 保护 _updated 与 _value 的原子性
    std::chrono::...::time_point _updated;
    double _value = 0;
};

为什么 HostSensor 要同时继承 Sensor 和 ValueObject？

因为它描述的是「外部系统主动推给我们的传感器」——宿主 BIOS / OEM 通过 /xyz/openbmc_project/extsensors/ 命名空间下的 Sensor.Value 接口把温度写进来。 对 Zone 而言它就是一个普通传感器（read() 返回上次推来的值）；对外部系统而言它是一个可写的 D-Bus 属性。 双继承让这两种身份共享同一份状态，而不是让 Zone 去订阅一个 D-Bus 信号再同步到别处。

收益外部推值路径最短：D-Bus setter → _value → Zone 的 read()，中间无队列无拷贝。
代价这是全库唯一需要 std::mutex 的传感器类：D-Bus 服务的 setter 线程与 PID 循环线程不同源，必须保护 _updated + _value 这一对（只保护一个会产生「新值配旧时间戳」的撕裂）。
注意 HostSensor::_value 初值 = 0：源码注释明确写了「a 0 value is ignored in FanController::inputProc()」。 也就是说 0 被当作「尚未有值」的哨兵，而不是一个合法转速。这是作者在缺少「可选值」类型时的务实取舍，也让「主机还没启动」这个状态自动退化为安全侧。
03路径字符串即类型：build_utils 的前缀派发

配置里只有 readPath / writePath 两个字符串，没有「接口类型」字段。作者用前缀匹配把路径翻译成枚举，再翻译成适配器。 这是一个刻意的简化：让 JSON 对用户保持极简（只写路径），把复杂度关在代码里。

为什么同一个路径在 read 与 write 两侧会得到不同的枚举（EXTERNAL / DBUSPASSIVE vs DBUSACTIVE）？

因为「读」与「写」的语义不对称：读 D-Bus 传感器意味着订阅别人的值（passive listener），写 D-Bus 意味着我们成为被观察者（active writer 去驱动 Fan.Speed 之类的属性）。 extsensors 命名空间是第三种：那里的值是外部主动推给我们，所以读侧要变成 HostSensor（我们提供服务），写侧却仍然是普通 active 写。路径前缀承载的是「拓扑位置」，不是「数据类型」。

收益JSON 配置零冗余，运维只需知道路径。
代价拼写错误（例如漏掉尾部 /、或 extsensor 少个 s）会静默降级成 UNKNOWN 而不是报错，故障表现为「传感器一直是 NaN / fail-safe」，很难定位。

max > 0 的含义：百分比模式 vs 原始模式sensors/builder.cpp

写侧选择 *Percent 变体的唯一依据是 cfg.max > 0。作者用它同时表达两件事：「这个 PWM 通道的量程是 min..max」 与 「请把 PID 输出的 0~100 百分比换算成原始寄存器值」。 当 max == 0（默认值）时退化为原始写法，适配器直接把值写出去。同一个字段承担两种语义是这套配置的一个历史包袱，但它避免了再加一个 percentMode 布尔。

另外，from_json 对 min/max 做了显式防御：非 fan 类型如果写了这两项，会打印 "Non-fan types ignore min value specified" 并丢弃。 这印证了设计边界——只有风扇是可写实体，其他传感器（temp / margin / power / powersum）一律配 ReadOnlyNoExcept。

04SensorManager：全局注册表与按类型索引

manager.hpp 只有 69 行，但它决定了整个系统的并发模型与 D-Bus 拓扑。 

class SensorManager
{
  public:
    static constexpr auto SensorRoot = "/xyz/openbmc_project/extsensors";

    SensorManager(sdbusplus::bus_t& pass, sdbusplus::bus_t& host)
        : _passiveListeningBus(pass), _hostSensorBus(host)
    {
        // 在 host 总线上注册 extsensors 命名空间，供外部写入
        _hostSensorBus.get().request_name(...);
        server::manager_t(_hostSensorBus, SensorRoot);
    }

                   std::unique_ptr<Sensor> sensor);

  private:
    std::map<std::string, std::unique_ptr<Sensor>> _sensorMap;   // 名字 → 传感器
    std::map<std::string, std::vector<std::string>> _sensorTypeList; // 类型 → 名字列表

    std::reference_wrapper<sdbusplus::bus_t> _hostSensorBus;

为什么是「两条总线」？

总线角色用途
_passiveListeningBus consumer 所有 DbusPassive 适配器在这条总线上 match 别人的 PropertiesChanged，把值缓存下来。它只读。
_hostSensorBus provider 我们是 /xyz/openbmc_project/extsensors 的 服务端，HostSensor 对象挂在这条总线上等外部写值。

把「我读别人」和「别人读我」放在不同总线上，是为了避免拓扑自环：如果同一条总线既订阅又发布，一个名字冲突或一次重入的信号处理就可能让值在环里打转。 分开之后，DbusPassiveRedundancy（多路传感器冗余投票）也可以安全地在 consumer 侧做汇聚，而不必担心把自己发布的对象当成输入。

为什么 fan 要额外挂 DbusPassiveRedundancy？

builder.cpp 里有一个 static std::shared_ptr<DbusPassiveRedundancy>，首次遇到 passive 风扇时创建，之后所有风扇共用同一个实例。 这解决的是「同一个风扇被多路传感器/多路主机上报，需要做冗余仲裁」的问题：冗余器必须看到所有风扇的变化才能投票，所以它天然是全局的，不能每风扇一个。 而温度传感器不需要投票（值本身无歧义），因此不传这个参数。

为什么 getSensor 用 .at()（抛异常）而不是返回 nullptr？

因为「zone 配置引用了不存在的传感器」是配置错误，不是运行时状况。运行时的「传感器坏了」由 fail-safe 机制表达（返回 NaN + 进 fail-safe 表）， 而「传感器根本没配置」必须立刻炸掉，否则 PID 会拿着空指针继续算，把风扇推到不可预测的占空比。

收益把配置错误与运行故障两类问题分开：前者崩溃暴露、后者优雅降级。
代价.at() 抛出的是 std::out_of_range，消息里没有传感器名，定位需靠外层 buildZones 已经打印的 PID name / inputs 日志。

接口分组的用意

分组主要调用者说明
遥测与缓存pidloop驱动侧只调这几个：每个 fan cycle 调 updateFanTelemetry，每个 thermal cycle 调 updateSensors。所有 I/O 都在这里发生。
setpoint 协议ThermalController / StepwiseController热控 PID 向风扇 PID 传值的唯一通道。接口注释写得很直白：「Fan PIDs are fed set points from Thermal PIDs」。Controller 之间没有直接引用。
fail-safeFanController风扇控制器在每个周期问 zone「现在是否 fail-safe、占空比该是多少」，而不自己维护失效状态。
模式D-Bus / FanControllergetManualMode() 让 pidloop 直接短路整个循环；getRedundantWrite() 让退出手动后强制重写一次 PWM。

为什么 ZoneInterface 要胖到 30+ 个纯虚函数，而不是拆成几个小接口？

因为它的消费者只有一个族（Controller），而 Controller 需要的能力确实就是「读缓存、加 setpoint、问 fail-safe、取时序」这几类。 拆成 ICache / ISetPointSink / IFailSafe 会让 createFanPid() 之类的工厂签名膨胀成四个参数， 而收益（更细的 mock 粒度）在只有三种 Controller 的现实下并不明显。作者选择了「一个胖端口 + 一个实现」， 把解耦压力转移到「Controller 不依赖 DbusPidZone」这一条上——这一条才是真正有价值的。

收益Controller 侧代码干净（一个 _owner 指针搞定所有交互），工厂函数签名简单。
代价测试必须实现 30+ 个纯虚函数才能 mock 一个 zone；接口变更的影响面覆盖全部 Controller。

06一个控制周期的生命周期

pidControlLoop 是一个 asio 递归定时器：每周期结束时把 timer->expires_at(nextTime) 推到原始到期时间 + 周期， 而不是「现在 + 周期」。注释解释了原因：防止 CPU 执行时间把周期越拖越长。

initializeLog() · 仅首周期
写 CSV 表头：epoch_ms,setpt,requester + 每个风扇 name,name_raw,name_pwm,name_pwm_raw + 每个温度点 name,name_raw + failsafe。表结构在启动时一次性确定，之后只追加行。
initializeCache() · 仅首周期
所有输入缓存填 NaN，并对每个输入主动调 markSensorMissing(name, "") —— 即「启动即 fail-safe」。这样在第一个真实读数到来之前，风扇走安全占空比而不是 0% 或满速。
getManualMode() · 每周期
若为手动模式，直接递归下一周期，跳过全部读写。手动模式下 zone 完全不碰硬件，把控制权交给外部（通常是运维通过 D-Bus 直接写 PWM）。
updateFanTelemetry() · 每 fan cycle
按 _fanInputs 读每个风扇转速 → processSensorInputs<true>()。模板参数 true 表示「这是风扇，日志里要并排记 PWM」。同时输出上一周期的 PWM 与 RPM 对照。
updateSensors() · 每 thermal cycle
processSensorInputs<false>() 读温度 / margin / 功率。用 false 因为热传感器没有 PWM 输出。
clearSetPoints() + clearRPMCeilings()
清空上一轮所有热控 PID 提交的 setpoint 与 RPM 上限，并复位 _maximumSetPoint。这是「每轮重新投票」的语义——没有累积状态，也没有滞后。
processThermals()
遍历 _thermals（ThermalController + StepwiseController），每个 process() 内部读缓存、算输出、调 _owner->addSetPoint() / addRPMCeiling()。
determineMaxSetPointRequest()
仲裁：先被 rpmCeilings 的最低值截断（名字记为 "Ceiling"），再被 minThermalOutput 托底（名字记为 "Minimum"），最后决定 _maximumSetPointName（即 leader()）。
processFans()
遍历 _fans，FanController 用 getMaxSetPointRequest() 作为目标转速，算 PID、套 fail-safe 下限、调 write()。之后清 _redundantWrite（一次性标志）。
writeLog() · 每周期
追加 ,failsafe 列，结束本行。

为什么风扇慢不了（10Hz），而热控可以慢（1Hz）？

因为两者的被控对象惯性不同：风扇转速环的响应时间在百毫秒级，必须快；而温度是热容积分量，秒级变化都很小，跑太快只会让 PID 的微分项被噪声主导。 把两个时间常数分开配置、并在同一个循环里按比例调度，比开两个线程更省资源，也避免了两个线程同时访问 zone 缓存所需的锁。

收益单线程、零锁、时序严格由 asio 保证。
代价如果某个 process() 阻塞（例如一次慢 D-Bus 调用），整个 zone 的风扇与热控都被拖住——没有隔离。
07fail-safe 模型：用「集合」而不是「布尔标志」表达状态

这是全篇最精妙的一处设计。DbusPidZone 没有 bool _failSafe，而是维护一张 FailSafeSensorsMap = map<string, pair<string, double>>， 语义是「当前处于失效的传感器 → (原因, 该传感器要求的占空比)」。于是： 

// 状态判定就是一次 empty()
bool DbusPidZone::getFailSafeMode() { return !_failSafeSensors.empty(); }

// 进入：写入 name → (failReason, percent)
void DbusPidZone::markSensorMissing(const std::string& name,
                                    const std::string& failReason)
{
    if (_missingAcceptable.count(name)) { /* 白名单：只记日志，不进 fail-safe */ return; }

    // 单传感器覆盖 > zone 默认
    double pct = _sensorFailSafePercent[name] != 0
                     ? _sensorFailSafePercent[name] : _zoneFailSafePercent;
    _failSafeSensors[name] = std::make_pair(failReason, pct);
}

// 恢复：擦除即恢复，无需额外状态迁移
else { _failSafeSensors.erase(sensor); /* “The sensor has recovered.” */ }

为什么不用一个布尔标志 + 一个失效计数器？

因为风扇控制器需要知道「是谁坏了」和「该给多少占空比」。布尔标志只能回答「要不要 fail-safe」， 一旦要回答「给多少」，就得再挂一张表与布尔标志同步——两个状态源必然出现不一致。让集合本身成为唯一真源， getFailSafeMode() 是派生量、getFailSafeSensors() 是同一份数据、恢复只是 erase，不可能不一致。

收益状态迁移零成本（插入/删除），多传感器同时失效自动合并，恢复语义天然幂等。
代价每次判定要 empty()（O(1)，可忽略）；但 map 分配在热路径上（每周期可能插入/删除），有轻微堆开销。

三级兜底：从「谁要求的」到「最终给多少」

层级来源数据结构规则
L1 单个 PID 的 failSafePercent（JSON 里每条 PID 可配） _sensorFailSafePercent 多个 PID 引用同一传感器时取最大值（addPidFailSafePercent 里 std::max）——更保守者胜。
L2 zone 级 ZoneConfig.failsafePercent _zoneFailSafePercent L1 没配（= 0）时回退到此值。
L3 所有失效传感器的最终仲裁 getFailSafePercent() 在整张表上取最大的 percent；若该最大值仍为 0，则再退回 _zoneFailSafePercent。 
double DbusPidZone::getFailSafePercent()
{
    if (_failSafeSensors.empty()) return _zoneFailSafePercent;

    // 注意比较的是 pair.second.second（percent），取最大
    auto maxData = std::max_element(_failSafeSensors.begin(), _failSafeSensors.end(),
        [](const FailSafeSensorPair& a, const FailSafeSensorPair& b) {
            return a.second.second < b.second.second;
        });

    // 全为 0 时兜底到 zone 默认（源码注明 dbusconfiguration.cpp 的默认值是 0）
    if (maxData->second.second == 0) return _zoneFailSafePercent;
    return maxData->second.second;
}

方向性：始终取最大。这是一个安全关键选择——多个传感器同时坏掉时，如果取平均或取最小，可能出现「一个要求 80%、一个要求 30%，折中成 55%」的欠冷却结果。 取最大则保证任何一个失效源都能单方面把自己的安全值拉满。

白名单：_missingAcceptable

JSON 里每个输入可以标 "missingIsAcceptable": true，进 addFanInput(..., missingAcceptable) / addThermalInput(...) 时被塞进 _missingAcceptable 集合。 markSensorMissing 开头就检查这个集合，命中则只打日志不改变 fail-safe 状态。

典型用途：整机上某些温度点是可选硬件（某个 SKU 没有那张卡）。如果不加白名单，机器一上电就永久 fail-safe，风扇长期在安全占空比、噪声大且费电。 白名单让「可选但确实没有」与「应该有但坏了」在配置层面区分开。

超时语义：风扇 0 秒，其他 2 秒

if (sensor->getFailed())
{
    markSensorMissing(name, sensor->getFailReason());        // 适配器主动报告坏了
}
else if (timeout != 0 && duration >= period)
{
    markSensorMissing(name, "Sensor timeout");            // 数据太旧
    outputFailsafeLogWithZone(..., "The sensor has timed out.");
}
else
{
    _failSafeSensors.erase(name);                            // 恢复了
    // “The sensor has recovered.”
}

Sensor::getDefaultTimeout() 里 fan → 0 的用意是：风扇转速为 0 是一个合法状态（风扇停转、或者整机待机）， 而「风扇该报数但没报」由 getFailed() 而不是超时来判定。温度 / 功率则相反——2 秒没更新就一定意味着数据源卡住了。

恢复是隐式的。代码里没有 markSensorRecovered() 这样的函数，恢复的唯一动作是「这一轮没有触发任何一个失效分支」→ 顺手 erase。 这让「恢复」不可能被遗忘，也不需要额外的状态机；但它也意味着一次瞬时的读取成功就能把传感器踢出 fail-safe，没有去抖（debounce）。 作者把去抖留给 FanController 的 failSafeTransition 日志，而不是状态本身。

日志限速：allowThrottle

// zone.cpp 文件级静态
bool allowThrottle(const tstamp& now, const std::chrono::seconds& pace)
{
    static tstamp then;
    static bool first = true;
    if (first || now - then >= pace) { then = now; first = false; return true; }
    return false;
}

传感器失效时，markSensorMissing 会被以 10Hz 的频率反复调用。如果没有限速，一个坏风扇能在几秒钟内把 journal 灌满并把 CPU 吃在格式化字符串上。 allowThrottle 把它压到每 3 秒最多一条（用于 tuning setpoint 文件读取的告警）。注意它用函数级 static 而非成员变量——说明作者把它当作「进程级噪声抑制」，而非 per-zone 状态。

08双级缓存：输入缓存与输出缓存为什么分开

DbusPidZone 里有两张同类型（map<string, ValueCacheEntry>）的表，名字只差一个词：_cachedValuesByName 与 _cachedFanOutputs。 它们服务的是完全不同的读取者。

缓存写入者读取者用途
_cachedValuesByName processSensorInputs()
（读传感器后立即写）		 getCachedValue(s)() → Controller 控制回路的唯一数据源。Controller 从不直接调 sensor->read()，只查这张表。保证一轮循环内所有 PID 看到的是同一时刻的快照。
_cachedFanOutputs setOutputCache()
（FanController 写完后回填）		 updateFanTelemetry() 的日志分支 仅供日志与可观测性。把「上一周期我们命令的 PWM」与「这一周期读到的 RPM」并排写进 CSV，方便画图分析闭环行为。

为什么一个 ValueCacheEntry 要同时含 scaled 与 unscaled

struct ValueCacheEntry
{
    double scaled;    // 归一化到 (0.0, 1.0)，用配置的 min/max 换算 —— PID 用这个
    double unscaled;  // 原始值 —— 日志、D-Bus 调试、恢复 RPM 时用这个
};

把两者放进同一个结构而不是两张表，是为了保证 「同一时刻的归一化值与原始值必定成对」。 如果分成两张 map，某次读取只更新了一张，PID 就会拿着新的 scaled 配旧的 unscaled，日志里出现无法解释的错位。 FanController::inputProc() 的注释也印证了这点：它会「Read the unscaled value, to correctly recover the RPM」。

NaN 初始化与「启动即安全」

void DbusPidZone::initializeCache()
{
    auto nan = std::numeric_limits<double>::quiet_NaN();
    for (const auto& f : _fanInputs)
    {
        _cachedValuesByName[f] = {nan, nan};
        _cachedFanOutputs[f]  = {nan, nan};
        markSensorMissing(f, "");       // ← 启动即 fail-safe
    }
    for (const auto& t : _thermalInputs)
    {
        _cachedValuesByName[t] = {nan, nan};
        markSensorMissing(t, "");
    }
}

为什么启动时把所有传感器预置成 fail-safe，而不是从 0 开始？

pidloop.cpp 的长注释讨论过这个问题，并给出了结论：「Another approach would be to start all sensors in worst-case values, and fail-safe mode and then clear out of fail-safe mode once we start getting values. Which I think it is a solid approach.」 对比另一种做法（等第一个读数到来再决定），「启动即 fail-safe」把最坏情况放在最前面：上电瞬间风扇就已经在安全占空比，之后每个传感器读数成功就自动被 erase 出表。 如果反过来，从上电到第一个读数之间风扇会是 0%，这在真实机箱里可能几秒钟就把 CPU 烤了。

收益安全侧默认，且恢复逻辑与正常路径共用同一段代码（erase），不需要特判「启动阶段」。
代价开机瞬间全速/安全转速的噪声；若配置把 failsafePercent 设得很高，用户会觉得「刚上电风扇就狂转」。
09setpoint 聚合与仲裁：热控 PID 如何「投票」给风扇

这是 Zone 模型里唯一的「多对一」通道：N 个热控控制器每轮各自提出一个目标转速，Zone 负责把它们合并成一个数字交给风扇 PID。 作者提供了两种合并语义，由一个 zone 级开关切换。

模式开关合并规则
取最大（默认） _accumulateSetPoint = false 每个 addSetPoint() 与当前 _maximumSetPoint 比较取大；并列时先到者胜（名字只记第一次的那个）。语义是「谁最热，听谁的」。
累加 _accumulateSetPoint = true 先做前缀剥离：Linear_Temp_CPU0 → Temp_CPU0（name.substr(name.find('_') + 1)），同 profile 的多个控制器输出相加。 
void DbusPidZone::addSetPoint(double setPoint, const std::string& name)
{
    if (!isPidProcessEnabled(name)) return;   // 运维通过 D-Bus 禁用的 PID 不参与投票

    if (getAccSetPoint())
    {
        auto profileName = name.substr(name.find('_') + 1);  // 去掉算法前缀
        setPoints[profileName] += setPoint;
    }
    else if (setPoint > _maximumSetPoint)
    {
        _maximumSetPoint     = setPoint;
        _maximumSetPointName = name;
    }
}

累加模式解决的是什么问题

当一个温度点同时被 PID 与 Stepwise 控制（源码注释：One sensor may have stepwise and PID at the same time）， 两者都希望对这个 profile 出力。取最大会丢掉其中一路的贡献（stepwise 通常给出阶梯值，PID 给出平滑修正），累加则把「阶梯 + 修正」叠加起来。 determineMaxSetPointRequest() 里还有一段配套逻辑：累加模式下要把最终 leader 名字拼成 "PID_xxx + Stepwise_xxx"，让日志能看出是谁合力的。

三级仲裁顺序（顺序不可换）

① 热控投票
addSetPoint() × N addRPMCeiling() × N
determineMaxSetPointRequest()
② 硬上限
rpmCeilings 取最小 → 截断，leader = "Ceiling"
minThermalOutput 托底
③ 硬下限
若 setpoint < minThermalOutput → 抬到下限，leader = "Minimum"
_maximumSetPoint / _maximumSetPointName
④ 消费
FanController: getMaxSetPointRequest() D-Bus: leader()

顺序是「先截上限、再托下限」。如果反过来，一个极高的 ceiling 会被 min 托底逻辑覆盖掉，上限就失效了。 这个顺序保证了「minThermalOutput 是绝对不能低于的底线，ceiling 是不能超过的天花板，两者冲突时下限优先」—— 在散热场景里，欠冷却（温度失控）的后果永远比过冷却（噪声）严重。

手动模式的退出语义：_redundantWrite

void DbusPidZone::setManualMode(bool mode)
{
    if (!mode) { _redundantWrite = true; }   // 从手动切回自动
    _manualMode = mode;
}

手动期间 zone 完全不写 PWM，所以它的「期望值」与硬件实际值出现分叉。切回自动时，如果 PID 算出与上次写入相同的 PWM， 常规优化（不变则不写）会让硬件继续停留在手动期间设置的值上。_redundantWrite 就是用来强制写一次的标志， 由 processFans() 在消费后清零——一个典型的「一次性标志 + 消费即清」模式，避免重复写。

注意 isPidProcessEnabled 的实现有隐患：它写的是 _pidsControlProcess[name]->enabled()， 用 operator[] 会在表里插入空指针（若名字不存在），随后解引用即崩溃。而它被 addSetPoint 在热路径上调用。 现实中能走到这里说明 buildZones 已为该 PID 建过 ProcessObject，所以不会触发；但这是一个「靠构造顺序保证正确性」的隐式契约。
10配置两段式：conf::* 作为唯一中间模型

作者没有让 JSON 直接构造运行时对象，而是引入了 conf.hpp 一层纯数据结构。这一层的价值在于： 同一个中间模型可以同时服务静态 JSON 与 entity-manager 动态配置，而运行时对象完全不需要知道自己的配置从哪来。

conf 结构从哪来变成什么关键字段
conf::SensorConfigfan-info.json 的 sensors[]一个 Sensor（Pluggable 或 Host）type / readPath / writePath / min / max / timeout / ignoreDbusMinMax / unavailableAsFailed / ignoreFailIfHostOff
conf::ControllerInfozone 的 pids{}一个 Controllertype / inputs[] / setpoint / pidInfo / stepwiseInfo / failSafePercent
conf::SensorInputPID 的 inputs[]zone 的输入名 + 名字装饰name / convertMarginZero / convertTempToMargin / missingIsAcceptable —— 这三个装饰项来自 PID 配置而非 Sensor 配置，注释明确说是为了兼容 entity-manager 动态传感器
conf::ZoneConfigzone 配置构造参数minThermalOutput / failsafePercent / cycleTime / accumulateSetPoint
conf::CycleTimezone 配置两个整数cycleIntervalTimeMS = 100 / updateThermalsTimeMS = 1000（默认值即设计意图）

为什么 SensorInput 要把 missingIsAcceptable 这类「装饰」放在 PID 配置里，而不是传感器配置里？

因为同一个传感器在不同 PID 里的重要性不同：CPU0 温度对「风扇曲线 A」是必须的，对「风扇曲线 B」可能只是参考。 如果把 missingIsAcceptable 放在 SensorConfig，它就成了全局属性，无法按用途区分。 更实际的原因是注释里写的：要让这套机制能用于 entity-manager 动态创建的传感器——那些传感器的 SensorConfig 不是我们写的， 我们只能在 PID 侧（我们自己的配置）里补充语义。

收益同一物理传感器可被不同 PID 以不同严格程度引用。
代价「这个传感器缺失是否可接受」的最终结果取决于「哪个 PID 也引用了它」——语义分散在多处，排查时要在 PID 配置里翻。

构造顺序（buildZones 内的隐式依赖）

make_shared<DbusPidZone>(...)
先建 zone 骨架，传入 mgr 引用、modeControlBus、对象路径、deferSignals=true。此时 D-Bus 上还看不到它。
按 ControllerInfo.type 分派
"fan" → FanController + addFanInput；isThermalType() → ThermalController + addThermalInput + addPidControlProcess；"stepwise" → StepwiseController。
addPidFailSafePercent(splitNames(inputs), info.failSafePercent)
在 zone 侧登记「这些传感器如果坏了，至少要给多少」。注意是逐个传感器登记，所以一个 PID 的多个输入会共享同一个 failSafePercent。
zone->emit_object_added()
全部 PID 装填完毕后一次性发布。这是 deferSignals 的收口点。
zones[zoneId] = std::move(zone)
交给 main.cpp 的容器，随后为每个 zone 各起一条 pidControlLoop。
构造顺序即正确性：isPidProcessEnabled() 依赖 _pidsControlProcess[name] 已存在（见 §09 的隐患）， 而它只在 ThermalController / StepwiseController 分支里被 addPidControlProcess 填充。 也就是说「只有热控类 PID 才会被 addSetPoint 的 enabled 检查覆盖，风扇 PID 跳过检查」——这是代码结构隐含的行为，没有任何注释说明。
