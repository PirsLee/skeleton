# pid.hpp

场景：

每次调用pid()函数时，传入同一个pid_info_t*，函数读写它内部的状态来完成控制循环。

pid_info_t

这是一个PID控制器的**运行实例**。包含**配置**，也包含**运行时状态**。

pidinfo

这是一个配置视图，**不包含运行时状态**，那么一个运行实例与配置区别为：

- initialized：是否初始化

- integral：积分误差

- last_output：最后一次输出的值

可配置项：

- ts 采样周期

- p_c 比例过程系数

- i_c 积分过程系数

- ff_off 前馈项偏移系数

- ff_gain 前馈增益

- i_lim 限制积分过饱和

- out_lim 限制输出超限

- slew_neg 输出增大，一次最多涨多少

- slew_pos 输出减小，一次最多减小多少

pid()

这是PID控制器的计算函数。输入当前测量值input和目标值 setpoint，返回控制输出。它是有状态的——通过 pidinfoptr读写积分项和上次输出。

风扇转动方向。

# controller.hpp

controller比pid多了input的来源、setpoint的来源、output去向、生命周期。也就是说pid是纯计算函数，而controller是加上了PID的参数控制。

PIDController

这是一个PID控制器的抽象基类。它定义了“一个PID控制循环应该长什么样”的骨架，但不关心具体控制什么物理对象。

当前的pid_process从哪里读取input？从哪里获取setpoint？输出output到哪里？这是由具体的controller决定的。

这种属于**模板方法模式**，pid_process()是模板方法——它定义了控制循环的固定流程，但把三个步骤延迟到子类实现：

```
父类控制流程，子类提供细节。这样：

控制流程不变（PID 算法永远按这个顺序跑）

硬件绑定可变（不同子类绑定不同传感器和执行器）
```

# fancontroller.hpp

一个`FanController`是一个PID Controller，读取多个fan的PID状态，PID算出一个输出值之后，尝试把风扇写入到那个值，这个setpoint不是由FanController决定的，而是由上层的ThermalController决定的。

fan是一个执行器，量是转速，thermal是因变量，量是温度，温度变化和转速变化不统一，不能用同样的setpoint

`FanController`里面的static方法，作用域在这个类中，属于工厂模式。不过这个static方法有一个特殊的属性：*不需要创建对象实例就能调用*：

```C++
SomeFanController = FanController::CreateFanPid(...)
```

如果是一个成员函数，那么将会非常奇怪：

```C++
fanController = FanController()
fanController.CreateFanPid()?
已经是一个fan控制器了，再创建一个根本没有这样的逻辑。
```

父类型是PIDController：
调用方只知道它拿到了一个 PIDController，可以调 pid_process()。它不知道也不关心背后是风扇、加热器还是水泵。这就是多态的好处——而静态工厂方法是创建多态对象的标准做法。

之所以这样是因为流程是标准的统一的，不需要子类继续实现了。

# zone.hpp

PIDZone的思想是怎么来的？

多个控制回路需要共享稀缺的执行器。PIDZone把传感器、温控 PID、风扇 PID、仲裁逻辑、安全策略、D-Bus 接口全部封装在一个"区域"里，让每个区域能独立运行、独立管理、独立暴露给外部。这是从一对一 PID 的朴素方案，经过共享资源冲突、安全需求、可管理性需求，一步步演化出来的架构。

朴素的PID控制架构：

```
温度传感器 A → PID → 风扇 1
温度传感器 B → PID → 风扇 2
温度传感器 C → PID → 风扇 3
```

这样朴素的PID架构会出现问题：

- 一个fan可以给多个热源散热，多个热源冲突，到底先给哪个散热

- 一个热源需要多个fan散热，fan数量不够

- 传感器失效，如果一个传感器坏了，那么就无法散热了

- 不同热源的散热需求不一样

```
温度传感器 A → Thermal PID → "我需要 X 冷却量"
温度传感器 B → Thermal PID → "我需要 Y 冷却量"
温度传感器 C → Thermal PID → "我需要 Z 冷却量"
                         ↓
                   仲裁/聚合
                         ↓
                   "风扇需要转到 RPM = max(X, Y, Z)"
                         ↓
                   Fan PID → PWM
```

这部分需要一个对象来做仲裁和聚合，谁来？PIDZone

- Thermal Controller是多热，需要多少冷量

- Fan Controller是根据冷量，需要怎么达到fan的setpoint

PIDZone的职责：

- 知道所有相关控制器的存在（谁能提供冷却需求？谁控制风扇？）

- 持有共享状态（传感器缓存——多个控制器读同一个温度传感器，不需要两次）

- 定义仲裁规则（取最大值？加权平均？优先级覆盖？）

- 统一调度（先跑温控PID，再仲裁，最后 跑风扇PID——顺序保证？）

- 统一管理安全策略（某个传感器失效时，整个区域进入安全模式）

PIDZone类比较复杂，拆解这样的类需要方法：

第一步：看继承——这个类是什么身份

```C++
class PIDZone : public ModeObject
```

继承了ModeObject，而ModeObject实现了ModeInterface接口。意味着：

**PIDZone同时是两个东西**

- 一个D-Bus对象，能够被外部通过D-Bus调用

- 一个PID Zone管理器

第二步：数据成员——这个类在管什么

|分组|成员|在管什么|
|---|---|---|
|身份|_zonId|“我”是第几号区域|
|风扇控制器容器|_fans|这个区域里所有fan的PID控制器|
|温控控制器容器|_thermals|这个区域里所有thermal的PID控制器|
|传感器缓存|_cacheValueByName|每次控制循环前读一次传感器，所有控制器共享|
|输入列表|_fanInputs, _thermalInputs|哪些fan、sensor属于这个区域|
|RPM聚合|_RPMSetPoints/_maximumRPMSetPt/_minThermalRpmSetPt|多个热区对风扇的冷却需求怎么合并|
|安全状态|_manualMode/_failSafePercent/_failSafeSensors|手动模式开关、安全模式阈值|
|外部依赖|_mgr/bus|传感器数据源、D-Bus总线连接|

第三步：函数成员

|分组|函数|职责|
|生命周期|constructor / initializeCache / dumpCache|初始化传感器缓存|
|添加控制器|addFanPID / addThermalPID|往容器里塞控制器|
|添加输入|addFanInput / addThermalInput|注册哪些传感器、风扇属于我|
|核心循环|process_fans() / process_thermals() |遍历所有控制器，逐个调取pid_process()|
|数据更新|updateFanTelemetry / updateSensors() | 从硬件、传感器读取最新值到缓存|
|RPM仲裁|addRPMSetPoint()/determineMaxRPMRequest()|多个热区都要冷却时，取最大的需求|
|D-Bus接口|manual() / failSafe() override|响应外部的模式切换请求|
|查询|getSensor() / getCachedValue() / getZoneId() | 各种getter|

第四步：找主线——它的一次完整工作流

```
主要流程：
流程一：启动流程（程序启动时，一次性跑完）
流程二：单周期控制流程（每次定时器触发跑一遍）
```

```
特殊流程：
[1] 手动模式：
    外部管理工具
        setManualMode(true)
        ModeObject::manual(true)
        主循环检测到_manualMode == true后：
            跳过process_thermals()和process_fans()
            由外部直接通过D-Bus设置PWM值
[2] 安全模式：
    updateSensors() 检测到某个传感器超时
        _failSafeSensors.insert(sensor_name)
        failSafe()返回true
        主循环检测到fail-safe后：
            忽略PID输出，直接用_failSafePercent
            或者走一个更保守的固定转速策略
```
